# LeanBridge production ChatGPT plan transport

Approved direction: the user explicitly requested production integration after the successful OAuth/Astra spike, removal of Railway's Codex CLI, durable authorization/refresh, and mobile delivery. This carries the chosen architecture forward; no new hosting or billing provider is introduced.

Keep the existing owner-only Sites workbench, history/deletion, model/effort settings, editable image transcription, text-only formalization/repair and official LeanWeb verification. Public provider remains `codex` for compatibility, with `subscriptionTransport: chatgpt-plan`. Replace the runtime model and auth implementation; the production entrypoint must not import or launch the CLI adapter. Remove the CLI package from Docker. No API-key fallback.

Direct requests use the validated OAuth bearer at https://api.openai.com/v1/models and /responses, store:false, stream:true, input arrays, instructions/developer messages, strict JSON output and bounded SSE. Accumulate output_text deltas; only response.completed is success. Bound bytes and deadlines, serialize generation, preserve selected model/effort, reject unavailable models. All image calls run the existing OCR stage before text-only Lean generation.

Durable session: private /data/chatgpt-plan directory (0700), encrypted session file (0600, AES-256-GCM), separate random local key file (0600), stable host identifier, atomic write/fsync/rename. The private volume and filesystem permissions are the security boundary; co-located encryption does not protect against complete volume compromise. Never expose tokens in config/status/history/errors/logs, source or delivery artifacts. Keep /data/codex intact for rollback; do not use or refresh its CLI credentials.

OAuth refresh is request-driven before expiry, single-flight across concurrent status/model requests; replace the rotating refresh token and access/ID tokens together. Respect earliest_refresh_at. Network/5xx failures keep the current durable record and report temporary failure. Only terminal revocation/invalid refresh errors require reconnect. One Railway replica, with the mounted volume, owns refreshes. No desktop process is required after bootstrap.

Bootstrap: reuse the already-issued public client ID. The authorized owner starts setup from the existing workbench; the backend creates a 10-minute transaction containing state, nonce, PKCE and a one-use ticket. It returns a form payload to the desktop bridge. A POST form sends it to http://127.0.0.1:59255/connect without placing the ticket in a URL. The bridge pins the production backend and allowed workbench origin, sets a browser cookie, and navigates to the official authorization URL. The exact loopback redirect is /auth/callback. After verifying cookie/state locally, it forwards only code/state/ticket (and issued client_id if present) over HTTPS to POST /api/subscription/callback, which checks the transaction, exchanges the code with its saved verifier, verifies signature/issuer/audience/nonce/scopes, then encrypts the session. Durable tokens never enter browser JavaScript or local files. Setup callbacks are narrowly public, ticket-authorized, size-limited, single-use and locked during exchange; begin/status remain behind existing owner/backend authentication.

Alternative considered: preserve the CLI in Railway or run it elsewhere. Both conflict with the explicit request. A standalone permanently running desktop broker is also excluded. The one-time local bridge is solely OAuth setup and exits after completion.

Builder calls: fixed loopback port 59255 matches the proven registration path; backend-generated setup nonce and PKCE enable direct server exchange and durable storage without exporting pilot tokens. No user-account credential is copied from another app. The bootstrap is the app's own public OAuth client using the official authorization-code protocol, not a Codex Cloud VM.

Acceptance: security/refresh/stream/model tests; full existing suites/typecheck/build; CI image has neither Codex CLI nor Lean compiler and performs real LeanWeb positives/negative/sorry tests; deployment image matches commit; official grant imports to /data; actual refresh/restart persistence verified; subscription text and original-photo two-stage generation verified with real LeanWeb; mobile workbench/history/delete regression; report measured production memory separately from compilation-only CI memory. Do not announce full delivery until these pass.
